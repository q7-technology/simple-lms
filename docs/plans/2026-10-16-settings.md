# Simple LMS: Settings

**Goal:** everyday settings are changed by an admin on the desktop's
**Settings** screen, and take effect without a restart, instead of being
edited in `.env`. The design's Settings list is "sign-in methods, SMTP,
reminder days, webhooks, API keys"; webhooks and API keys arrive with step 6.

## Decisions

- **In the UI** (admin only): sign-in methods (code + PIN, email +
  password); the quiz wait (failed tries in a row before it, 1 to 20,
  default 3; minutes, 0 for none, default 60); reminder days (whole days 0 to
  365, at least one, default 30, 14, 0); the daily job's hour (0 to 23,
  default 6) and the time zone (an IANA zone, default Australia/Melbourne);
  the email server (host, port, user, password, from address, security);
  the public web address for links in emails.
- **Stays in `.env`:** what is needed before the app starts, or could lock
  everyone out: the database URL and password, ports, the domain, the upload
  folder, Caddy, and the worker's poll interval.
- **A `setting` table**: `key` (primary key), `value` (JSONB), `updated_by_id`
  (a person, nullable for the CLI), `updated_at`. Migration `0003b`, after
  `0003`; step 4's `0004` goes after `0003b`. Settings are mutable config,
  not the training record, so no append-only trigger; who changed each one
  last, and when, is kept on its row. No separate audit table (YAGNI).
- **Effective value** = the row if there is one ("set here"), else the
  `.env` value if `.env` gives one (".env"; one equal to the default says
  "default", as Compose passes every variable whether `.env` has it or
  not), else the default ("default").
  Existing deployments keep working untouched. Removing a row (sending
  `null`) goes back to `.env` or the default. Settings with no `.env`
  variable (the quiz's tries, reminder days, sign-in methods) are set here
  or default.
- **One reader:** `lms/services/settings.py` is the only place these values
  are read (`settings.current()`). It keeps the rows for 5 seconds, so the
  worker and every API process pick up a change within seconds; the API
  process that saved a change forgets its copy at once. The `.env` layer is
  read afresh each time from `lms.config`.
- **The email password is write-only:** never returned, shown as set or not
  set. Leaving it blank keeps it; **Clear** saves an empty one here (which
  also hides one in `.env`).
- **Sign-in methods:** a switched-off method is refused on sign-in with
  `403 { "code": "method_off" }`; sessions already open run out as usual.
  Lock-out guard: switching password sign-in off is `409 { "code":
  "last_way_in" }` while it is the only way an admin can sign in. A PIN
  session never carries admin scopes, so until Entra (step 5) adds a third
  switch, only PIN sign-in can be switched off, and the screen says so. The
  `lms` CLI never signs in, so it works whatever is switched off, and
  `lms clear-setting KEY` puts any setting back to `.env` or the default.
- **Reminder days:** the daily job sends the nearest reminder day not yet
  passed, as before, for anything with an expiry date within the largest
  reminder day. The outbox key keeps its shape
  (`reminder:<person>:<competency>:<expires_on>:<day>`), so every key queued
  before stays valid and nothing is sent twice.
- **Test email:** `POST /v1/settings/test-email` queues one email to the
  signed-in admin's own address through the outbox; the worker sends it
  within seconds. No email address, or no email server, is `409`.
- **API:** `GET /v1/settings` and `PUT /v1/settings` (partial; scope
  `settings:write`, which only `*` has), each answering every setting with
  `{ "value", "source": "here" | "env" | "default" }` (the password has
  `"set"` instead of a value). Bad values are `422` on their own field;
  nothing is saved unless all are good.
- **Desktop:** a Settings screen, linked only for an admin, in sections:
  Sign-in, Quizzes, Reminders, Email, Web address. Each field says where its
  value comes from, and each section saves on its own with a plain success
  or error message.
